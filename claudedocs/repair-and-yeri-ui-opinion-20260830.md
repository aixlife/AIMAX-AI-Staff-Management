## 1. 자동수리 — 왜 체킹만 되고 수정이 안 되나

**의도적으로 두 겹으로 꺼져 있다.** 고장이 아니다.

| 시점 | 일어난 일 |
|------|----------|
| 6/19~7/3 | 수리 에이전트 타이머 가동 — 그러나 중복 억제 버그로 **하루 91~92회 텔레그램 알림 폭주** |
| 7/3 17:33 | 커밋 `0f2ea59` — 수리 권한 제거, **분석·보고 전용**으로 축소 (스크립트에 "코드수정·커밋·재시작·배포 절대 금지" 명문) |
| 7/3 19:26 | 타이머 자체를 stop + disable — 이후 **57일간 실행 0회** (서버 실측) |
| 8/18 | `2924a5d` — 폭주 원인(알림 서명 불안정) 수정 완료, 서버 반영 확인. **타이머는 의도적으로 계속 꺼둠** |

- 지금 오는 "체킹" 알림 발신 주체 2곳: `aimax-report-watchdog.timer`(30분 주기, [AIMAX 오류 자동체킹] — enabled/active, 8/30 정상 동작 실측)와 접수 즉시 알림(server.js). 수리 에이전트와는 다른 유닛이다.
- 재가동은 `systemctl --user enable --now` 1줄이면 되지만, **켜도 코드가 보고만 한다.** 수리 권한 원복은 7/3 결정의 번복이라 민수 결정 사항.
- 더 큰 문제(8/18 분석): 이 감시는 "사람이 보낸 오류 보고"만 본다. 켜져 있었어도 당시 사고 3건(네이버 로그인 파손·현주 무성공 done 기록·v1.0.60/61 미배달) 중 **하나도 못 잡았다.**

**의견**: 재가동 순서는 (1) 지표를 서버 데이터 기반 5종으로 교체 — 잡 실패율 급증 / 동일 error·stage 코드 급증 / 특정 워커 실패 0 지속 / 플릿 버전 정체 / 카탈로그-번들 불일치 (2) 1시간 주기 + 상태 변화 시에만 보고 전용 재가동 (3) 자동 수정은 가역 조치(안내 재발송·잡 재큐잉)부터 계층적으로. 부수 정리 필요: 서버 타이머 15분 vs 리포 30분 드리프트, 실행 디렉토리가 미커밋 코드 있는 .openclaw 운영 체크아웃인 문제.

## 2. 예리 스타일 3종 — 왜 설정에 있나

**8/25 커밋 `69bfe5b`의 의도적 결정이다.** 근거는 기존 폼 옵션 실사용률: 손이 더 갈수록 급락.

| 옵션 | 실사용률 |
|------|---------|
| 카테고리 | 44% |
| CTA | 42% |
| SEO | 26% |
| 문체참고 | 8% |

→ "매번 고르라고 하면 대부분 기본값으로 간다"고 판단해 계정에 한 번 저장하는 방식을 택했고, 고르는 화면을 설정 탭에 넣었다.

**그 근거의 약점(조사에서 확인)**: 688건 중 675건이 기본값이었던 진짜 이유는 커밋 메시지 스스로 "고를 화면이 아예 없어서"라고 자인하고 있다. 즉 '글마다 고르게 했더니 안 골랐다'는 실측이 아니라, 선택지가 없던 시절 데이터다.

**구현 사실**: 서버 `handleCreateJob`은 이미 잡 payload의 `style_id`를 우선 적용하고 없을 때만 계정 저장값으로 폴백한다(server.js:18087-18090). **웹 폼에 select 하나 + 제출 payload 한 줄이면 서버 무변경으로 잡별 선택이 된다.**

**의견**: 둘 다 유지가 정답 — 설정의 계정 기본값은 그대로 두고, 글쓰기 폼 상단(키워드 바로 아래)에 "이번 글 스타일" 3카드를 넣는다. 기본 선택 = 계정 설정값이라 아무것도 안 고르면 지금과 동일하게 동작, 강제 단계가 늘지 않아 실사용률 하락 우려도 해소된다.

## 3. UI 전반 의견

조사에서 관찰된 구조 문제:

| 문제 | 근거 |
|------|------|
| 죽은 화면 — researchTab은 여는 버튼이 없고 액션은 jobs로 리다이렉트 | app.html:3701, 13455-13461 |
| 단일 파일 15,219줄 (HTML+CSS+JS) | app.html 전체 |
| 예리 폼 한 화면에 12개 옵션 그룹 — 실사용률 하락을 만든 구조 그대로 | app.html:3846-3937 |
| 설정 탭에 성격 다른 6종 혼재 (로컬설정·실행기·글쓰기 스타일·웹작업·AI/API·키 가이드) | app.html:4381-4551 |
| 유사 명칭 다른 기능 — "기존 작성글 스타일"(폼) vs "글쓰기 스타일"(설정) | app.html:3932 vs 4410 |
| 직원 6명 폼이 jobs 탭 안 hidden 토글 2차 내비 | app.html:3846-4369 |
| 반응형 브레이크포인트 2개뿐, 폼 그리드 좁은 화면 규칙 없음 | app.html:3086, 3097 |
| 스타일 카드 미리보기가 회색 스케치 — 실제 글 스크린샷 교체 미완 | app.html:12240-12266 |

**의견 — 순서가 핵심**:
1. **(즉시) 스타일 잡별 선택** — 위 2번. 최소 비용, 최대 체감.
2. **예리 폼 3단 재구성** — 실사용률 데이터가 이미 있으니 그 순서대로: 필수(키워드+스타일) / 자주 씀(발행·분량·이미지·카테고리) / 고급(접힘: SEO·CTA·문체참고·예약). 강제 없이 접기만으로 화면 부담을 줄인다.
3. **설정 탭 정리** — 산출물 성향(스타일·문체참고)은 작업 지시 화면으로, 설정에는 인프라(키·실행기·로컬)만. "기존 작성글 스타일" 명칭도 이때 통합.
4. **죽은 researchTab 제거**는 2~3과 같이. **15K 단일 파일 분리는 별도 라운드** — UI 변경과 섞으면 회귀 원인 추적이 안 된다.
