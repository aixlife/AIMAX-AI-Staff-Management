## 2. 왜 91회씩 돌았나 — 중복 억제가 죽어 있었다

수리 에이전트는 "같은 상황이면 24시간 안에 다시 알리지 않는다"는 억제 장치를 갖고 있었다.
그런데 그 판정 기준이 잘못됐다.

```bash
signature="$(printf '%s' "$WATCHDOG_JSON" | jq -r '.message' | sha256sum | awk '{print $1}')"
```

**알림 메시지 전문을 해시했다.** 그 메시지 안에는 이런 것이 들어 있다.

- `기준: 2026-07-03 10:23 UTC / 자동 재알림` — 현재 시각, 분 단위
- `(new, 3h 42m)` — 각 리포트의 경과시간

즉 **15분마다 서명이 무조건 달라진다.** 24시간 억제는 단 한 번도 발동할 수 없었다.

실제 로그가 그대로 보여준다. 같은 4건인데 서명이 다르다.

| 시각 | stale/티켓 | 서명 |
|---|---|---|
| 7/3 19:07 | 4 / 4 | `40f45def…` |
| 7/3 19:23 | 4 / 4 | `1c04b7fd…` |

역설적인 건, **watchdog 본체는 이미 제대로 하고 있었다는 점이다.**
`alert_signature()`는 리포트/티켓 id 로만 서명을 만든다(안정적).
그런데 그걸 JSON 출력에 넣지 않아서, 소비자인 수리 에이전트가 쓸 수 없었고 메시지를 해시할 수밖에 없었다.

**수정(커밋 `2924a5d`)**: watchdog 이 안정 서명을 `signature` 키로 내보내고, 수리 에이전트가 그걸 쓴다.
검증: 경과시간이 바뀌어 메시지가 달라져도 서명 유지, 리포트 집합이 실제로 바뀌면 서명 변경 (8건 PASS).

## 3. 더 중요한 문제 — 켜져 있었어도 못 잡았다

이게 핵심입니다. 오늘 라운드에서 찾은 실제 고장 3건을 이 감시가 볼 수 있었는지 따져봤습니다.

| 실제 고장 | 감시가 봤을까 | 왜 |
|---|---|---|
| 네이버 로그인 파손 (6월~8월, 23건 실패) | **못 봄** | 사용자 오류 보고가 8/17에야 1건 왔다. 그 전 실패들은 `naver_login_required`(사용자 조치 필요)로 분류돼 `waiting_user` 상태였고, 감시는 "방치된 리포트"만 본다 |
| 현주 서이추 무성공 보고 | **못 봄** | 실패가 서버에 `done`으로 기록됐다. 리포트도 티켓도 생기지 않는다 |
| v1.0.60·61 미배달 (4주) | **못 봄** | 배포 파일과 카탈로그 버전 불일치는 리포트·티켓 어디에도 나타나지 않는다 |

**감시가 보는 신호는 "사람이 보낸 오류 보고"다. 실제 고장의 극히 일부만 그 경로로 온다.**
사용자는 대부분 보고하지 않고 그냥 다시 시도하거나 떠난다.
반면 **실패 자체는 전부 서버 잡 데이터에 남아 있다.** 감시가 그쪽을 안 보고 있었다.

## 4. 제안 — 3단계

### 1단계. 지표를 "리포트"에서 "실패"로 옮긴다 (Phase 1 관측성과 함께)

리포트 기반 감시는 유지하되, 아래를 **주 신호**로 올린다.

| 지표 | 잡아내는 사고 |
|---|---|
| 잡 실패율 급증 (워커별·일별) | 오늘 같은 광범위 파손 |
| 동일 `error`/`stage` 코드 급증 | 선택자 파손, 모델 은퇴 |
| 특정 워커의 실패 0 + 성공률 100% 지속 | 현주형 "무성공 보고" 역탐지 |
| 플릿 버전 정체 (최신 버전 수신 0대) | v1.0.60/61형 미배달 |
| 카탈로그 LATEST ≠ 서빙 번들 | 같은 사고 (오늘 이미 추가) |

이 지표들은 전부 이미 서버에 있는 데이터로 계산된다. 새 수집이 필요 없다.

### 2단계. 보고 전용으로 재가동 (지표 교체 후)

- 주기 15분 → **1시간**. 15분은 사람이 반응할 수 있는 주기가 아니다
- 알림은 **상태 변화가 있을 때만**. "여전히 4건"은 알림이 아니라 대시보드에 있을 내용이다
- 한 사고당 최초 1회 + 24시간마다 1회 상한

### 3단계. 자동 수정은 그 다음 (지금은 반대)

오늘 라운드가 자동 수정의 한계를 보여줍니다. 로그인 버튼 수정에 필요했던 판단은
"실사이트를 렌더링해서 **보이는** 버튼을 골라야 한다"는 것이었고, 이건 정적 분석으로는 안 나옵니다.
숨은 버튼을 눌렀다면 예외도 없이 조용히 실패했을 겁니다.

자동 수정을 켜려면 먼저 **자동 검증**이 있어야 합니다.
Phase 1(정형 결과·단계 이벤트)과 Phase 3(발행 후 검증)이 깔린 뒤에 다시 논하는 게 맞습니다.
