## 2. 현주(서이추)는 실패를 "성공"으로 보고하고 있었다

조사 중 별건으로 확인. `app.py`의 원격 잡 처리에서 `hyunju_find`만 워커 결과를 **버리고** 무조건 `done`으로 보고하고 있었다.

```
yeri_write   → 결과 ok=False면 서버에 failed + 사유 전달  (정상)
hyunju_find  → 결과를 읽지 않고 항상 done                  (결함)
```

거기에 `_worker_neighbor` / `_worker_link_neighbor`는 내부에서 **모든 예외를 삼키고** 로그만 남긴다.
즉 네이버 로그인 실패로 터져도 → 예외 삼킴 → 결과 없음 → 서버에 `done`.

실측 근거: 8/17 사용자 오류 보고(`AIMAX-RPT-20260817103127`)에 연결된 현주 잡 3건이 **전부 `done`**.
사용자는 실패를 겪었는데 서버에는 성공으로 남았고, 자동 분류도 붙지 않아 보고가 하루 넘게 `접수됨` 상태로 방치됐다.

이 결함 때문에 **현주 쪽 실제 실패율은 지금 통계로 알 수 없다.** 수정 배포 후 1주일 관찰이 필요하다.

|---|---|---|

플릿 하트비트가 이를 그대로 증명한다. 등록된 111대 중 **v1.0.60·61은 0대**이고,
최근 30일 활성 23대는 **전원 v1.0.59**다.

즉 사용자는 4주 동안 "v1.0.61로 업데이트하세요" 안내를 보고, 눌러서 받고, 설치했지만
받은 것은 v1.0.59였다. 그래서 영원히 업데이트 안내가 사라지지 않았다.
v1.0.60·61에 들어 있던 AI 모델 최신화(Gemini 2.x 은퇴 대응)도 아무에게도 가지 않았다.

원인은 절차다. 태그 → CI 빌드 → 카탈로그 LATEST 상향까지는 했는데
**설치 파일 업로드 한 단계가 빠졌고, 두 값을 대조하는 곳이 없었다.**

재발 방지로 두 가지를 넣었다(커밋 `8632ec5`).

- 번들을 올리면 `aimax-bundle-versions.json` 에 버전·sha256 도장을 남긴다
- `scripts/verify_agent_catalog_consistency.py` 가 광고 버전 · 도장 · 현재 파일 해시를 대조하고
  불일치면 종료코드 1을 낸다 (감시 타이머에 물릴 수 있다)

서버 실측: `광고 v1.0.62 = 서빙 v1.0.62`, 일치.
